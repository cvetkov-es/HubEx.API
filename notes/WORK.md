# WORK — заметки практики

> **Что здесь:** проверенные практикой правила и грабли сервиса WORK (заявки). Сигнатуры ручек — [endpoints/WORK.md](../endpoints/WORK.md).
> **Когда сюда идти:** перед работой с заявками через API.

## Грабли

⚠ Нет единого понятия «незакрытая заявка» — `isClosed` и `isDeleted` независимы. `isClosed=false` сам по себе НЕ исключает мягко удалённые заявки: чтобы получить строго активные незакрытые, нужно явно комбинировать `isClosed=false&isDeleted=false`. Расхождение в счётчиках при добавлении/убирании `isDeleted=false` — ожидаемое поведение, не баг API (проверено эмпирически 4 комбинациями `isClosed`×`isDeleted` на живом тенанте).

⚠ То же самое для «невыполненная заявка» — `isCompleted` и `isDeleted` тоже независимы (стадии «Выполнена»/«Закрыта» разные). `isCompleted=false` без `isDeleted=false` тоже включает мягко удалённые. Правило общее: любой флаг из `taskFlags` (`isClosed`, `isCompleted`, ...) нужно комбинировать с `isDeleted=false`, если нужны строго активные заявки (проверено эмпирически на тенанте 342, 2026-07-06: 8132 против 13430).

⚠ `/Tasks/count` капризна к параметрам: без `dateFrom`/`dateTill` — `500 SqlDateTime overflow`; с ними вместе с `creationFrom`/`creationTill` — `409 InvalidDatePeriod`. Для простого «сколько заявок за период» надёжнее `HEAD /Tasks ?creationFrom&creationTill` и читать `Content-Range: items=0-0/{total}` из заголовка ответа.

⚠ `HEAD /Tasks` — отдаёт `Content-Range: items=0-0/{total}` **и без заголовка `Range`**, в отличие от `GET`-списков (общее правило «без `Range` нет `Content-Range`» в [overview.md](../overview.md) проверено на `GET`). Пустая выборка — тоже `200` с `items=0-0/0`, а не `204`. Проверено живыми вызовами 2026-10-12, тенант 185: `HEAD /Tasks?contractID=1&isCompleted=true&isDeleted=false` без `Range` и с `Range: items=1-1` → одинаково `200`, `items=0-0/1`; `contractID=2` → `200`, `items=0-0/0`.

⚠ Сортировка — пара `orderBy` (числовой id, только из ключа map `GET /TaskOrderBy`) и `sortDirection` с доменом **1 = asc, 2 = desc** объявлена у пяти WORK-ручек (`GET /Tasks`, `HEAD /Tasks`, `GET /Tasks/count`, `GET /Tasks/groupBy/geoHash`, `GET /Tasks/short`); без `sortDirection` — desc, без `orderBy` — сортировка по дате создания заявки (`timesheet.created`; в `GET /TaskOrderBy` эта запись — id 1, `name` «Дата подачи», `code` `CreationDate`). Самая свежая заявка — `sortDirection=2` без `orderBy` (проверено 2026-08-05, тенант 185, 3951 заявка: id 3993, 3992, 3991); с явным `orderBy=1` результат тот же, поскольку это и есть дефолтное поле.

⚠ Значение вне домена ведёт себя по-разному у двух параметров — проверено это только на `GET /Tasks`, для остальных четырёх ручек с этой парой не считать доказанным. У `sortDirection` вне домена (`0`, `3`) **молча выключается сортировка целиком**, вместе с `orderBy`: выдача идёт в натуральном порядке id (`orderBy=8&sortDirection=0` → id 1,2,3; для сравнения `orderBy=8&sortDirection=1` → id 2,21,23 по возрастанию `lastModified` — сортировка работает). У `orderBy` вне домена (`99`) сортировка **не выключается — откатывается только поле**, к дате создания: `orderBy=99&sortDirection=2` → id 3993,3992,3991, ровно как без `orderBy` вовсе (будь сортировка выключена, был бы натуральный порядок id 1,2,3). Строкой не принимается ни один параметр: `sortDirection=desc`, `orderBy=CreationDate` (это `code` записи id 1 из тела `GET /TaskOrderBy`, не число) → `409 InvalidData`, тело без указания параметра.

⚠ `GET /TaskOrderBy` отдаёт map, где id есть **только в ключе** (в теле — `name` и `code`), и id разрежены: проверено 2026-08-05 — 1,2,3,4,5,7,8, шестого нет. Позицией в списке id не заменить, а `code` из тела `orderBy` не принимает (`409`). Тот же капкан, что у `GET /Tasks`: `Object.values()` теряет идентификатор молча — брать `Object.entries()`.

⚠ Даты создания заявки нет под именем `creationDate` (0 совпадений во всём `schemas/WORK.md`) — она лежит в блоке `timesheet`: `timesheet.created`, и в списке `GET /Tasks`, и в карточке `GET /Tasks/{taskID}` (проверено 2026-08-05: `О0710000` → `timesheet.created` 2019-10-07 при `lastModified` 2025-06-24). Отсюда типовой ложный вывод «дату подачи по списку не получить»; сортировка `orderBy=1` работает именно по этому полю.

⚠ На практике `GET /Tasks/{taskID}/completedWorks/technicians` отдаёт не одиночный `CWTechResult`, а `map<CWTechResult>`, ключ — `completedWorkID` (по одной записи на каждую Выполненную работу заявки). Если у заявки нет Выполненных работ с исполнителями — `204 No Content` (не пустой массив).

⚠ У элементов списка `GET /Tasks` **нет поля `id`** — идентификатор заявки есть только в ключе map-ответа (проверено 2026-07-15: ключи `7102`, `7101`). Схеме это не противоречит — у `Tasks.ListResult` в swagger `id` тоже нет, — но на практике ловушка: клиент, разворачивающий map в массив через `Object.values()`, теряет идентификатор молча. Брать `Object.entries()` и класть ключ в `id`. Человекочитаемый идентификатор заявки — `number`. Для сравнения: у `GET /ES/Assets` (`AssetExtResult`) `id` лежит в теле значения. Перечень полей — [schemas/WORK.md](../schemas/WORK.md) (`Tasks.ListResult`).

⚠ `X-Concurrency-Stamp` — заголовок идемпотентности (Guid, до 255 символов, опционально), в swagger параметром **не объявлен** — описан только прозой в `description` операций, структурным разбором не обнаружить. Повтор запроса с тем же значением не создаёт вторую сущность, а отвечает `409`. **Где понимает (живые вызовы):** `POST /Tasks` (2026-09-09, тенант 1), `POST /CompletedWorks` (`409` на повторе), `POST /ES/Assets` — см. [notes/ES.md](ES.md). **Где не понимает:** `POST /COMMON/Attachments/upload/fromForm` — см. [notes/COMMON.md](COMMON.md); читающая `GET /TaskTypes` молча игнорирует заголовок (`200`, не `400`). `POST /TaskStagingHistory/batch` — до-заголовочная форма: обязательное поле `concurrencyStamp` в теле. `X-Suppress-Conflict: true` (→ `200` вместо `409` у `POST /CompletedWorks`) — знание из swagger-прозы, живьём не вызывался. Версию UUID сервер не проверяет (детерминированный `uuid5` принимается); не-Guid значение → `400` с пустым телом.

⚠ Форма `409` на повтор стампа **разная по ручкам**: у `POST /Tasks` — плоский объект той же формы, что `201` (`{"id", "number", "concurrencyStamp"}`), у `POST /CompletedWorks` — **массив** из одного элемента. Правило «плоский объект — коллизия, массив — бизнес-ошибка» поэтому неверно; надёжный признак коллизии — эхо отправленного стампа плюс `id` в теле. У `POST /TaskStagingHistory/batch` эха нет вовсе — см. ниже про смену стадии.

⚠ Свойства стампа на `POST /Tasks` (2026-10-07, тенант 1, четыре тестовые заявки, все удалены): (1) тот же стамп с **другим телом** — `409` с эхом первой заявки: сервер сравнивает стамп, а не тело, и существующую заявку не меняет; (2) **одновременные** отправки с одним стампом (3 пары) — ровно одна заявка, второй запрос пары получил `409` с эхом; номера проигравших пропускаются; (3) после **удаления** заявки тот же стамп отдаёт `409` с эхом **удалённой** — удаление стамп не освобождает; (4) **отклонённое** создание стамп не занимает: `409 InconsistentData`, затем исправленное тело с тем же стампом → `201`. Сколько сервер помнит стамп дольше минут замера — не измерено.

⚠ Смена стадии через `POST /TaskStagingHistory/batch` (2026-09-10, тенант 1): `202 {"isSuccessed": true, "batchID": …, "error": ""}` приходит **одинаково** на легальный переход (применяется) и на нелегальный (молча отбрасывается — восемь заявок, ни одна не сменила стадию, история не изменилась). По ответу эти исходы не различить — стадию надо перечитывать. Применение **отстаёт** от ответа: стадия в `GET /Tasks/{taskID}` и запись в истории появились через 4.5–7 с после `202` (по одному чистому наблюдению на двух тенантах, верхней границы нет); чтение сразу после ответа покажет старую стадию. Повтор с тем же `concurrencyStamp` → `409` массивом `[{"code": "InvalidOperation", "message": "Concurrency conflict"}]` — без эха стампа, неотличимо от настоящей гонки за стадию. Повтор с другим стампом → снова `202`, второй строки истории нет.

⚠ Одиночная `POST /TaskStagingHistory` на легальный переход — `201 {"stageId": …, "isFinalStage": false, "errors": []}`, строка истории видна сразу (поле стадии в `GET /Tasks/{taskID}` всё равно отстаёт на секунды); на нелегальный — громкий `409 InvalidData` «Нарушена целостность данных: Указанная стадия отсутствует в жизненном цикле заявки данного типа». Повтор того же перехода — тот же `409 InvalidData` (целевая стадия уже недостижима), второй строки нет. Поля идемпотентности у одиночной ручки нет (2026-09-10, тенант 1).

⚠ Легальность перехода до попытки проверяется только `GET /Tasks/{taskID}/stages/next` (map доступных стадий). `GET /TaskTypes/{taskTypeID}/route` отдаёт лишь `startTaskStage`/`finishTaskStage`, а не граф: стадия-финиш маршрута может быть недостижима из текущей. `stages/next` выполнимость требований стадии не проверяет — стадия была в выдаче и до назначения исполнителя, которого требовала (2026-09-10, тенант 1).

⚠ Автопереход стадии по таймауту (`timeoutSeconds` в `GET /TSTG/TaskStageLinks`) пишется в историю от пользователя 1, `applicationID: 3`, с текстом «Автоматический переход ввиду истечения отведённого срока»; по серверу задержка 8–64 с (медиана 13.5 с) при `timeoutSeconds: 5` (2026-10-15, тенант 192).

⚠ `isClosed` следует **закрытию** заявки (наличию `timesheet.closed`), а не статусу: заявка со статусом «Отменено» на промежуточной стадии — `isClosed=false`, после перехода на закрывающую стадию — `true` (2026-10-15, тенант 192).

⚠ `GET /Tasks/{taskID}` удалённой заявки — `200` с полем `deleted` (момент удаления). А `GET /Tasks/{taskID}/attributes` и `POST /TaskAttributes` по ней же — `409 [{"code": "TaskDeleted", "message": "Заявка удалена"}]` (2026-09-25, тенант 335; 2026-10-06, тенант 1).

⚠ `?erpID=` на `GET /Tasks/short` — **точное** совпадение: ключ `…:117` не находит `…:1170`, префикс не находит ничего. Несколько ключей — повторённым параметром (`erpID=A&erpID=B`, работает как ИЛИ); через запятую (`erpID=A,B`) — пустая выдача; `erpID[]=A` — незнакомое имя, молча игнорируется (вся выдача). Без `isDeleted=false` находит и удалённые (2026-10-06, тенант 1).

⚠ `attributeValues` на `GET /Tasks` — Base64 от JSON-массива `[{"ID": <атрибут>, "Value": "<значение>"}]`. Со `Value` ищется **вхождение** без учёта регистра и крайних пробелов, а не равенство (`455728` и `557288` находят `4557288`; `mc adg vITYAZ` находит `MC ADG Vityaz`; кириллица — тоже). Без `Value` (или `"Value": null`) — заявки с **заполненным** полем. Голое `attributeValues=39` — не фильтр (вся выдача), `39:` → `409 InvalidData`. Поведение подстановочных `%`/`_` не проверялось (2026-10-15, 2026-10-22, тенант 192).

⚠ `lastModifiedFrom`: значение без пояса читается как UTC, `Z` и `+03:00` пересчитываются; граница включительна, точность — секунда. Все даты заявок (`timesheet.*`, `lastModified`, `occured` истории) — UTC без указания пояса (2026-10-06, тенант 1; 2026-10-15, тенант 192).

⚠ `POST /Tasks` без `requestedByUserID` ставит инициатором владельца токена. На объект, чьи участки не совпадают с участками типа заявки, — `409 InconsistentData` «Участки типа заявки не соответствуют участкам объекта». На оборудование, у которого и у хоста нет локации, — `500 [{"code": "UnableToResolve", "message": "Cannot insert the value NULL into column 'CountryID', table 'HubEx.Actual.ES.Location'…"}]`, заявка не создаётся. При создании заявка получает **свою** строку локации — копию адреса объекта (2026-10-06, тенант 1; 2026-10-22, тенант 192).

⚠ `GET /Tasks/{taskID}/attributes` отдаёт **все** доп.поля заявки, незаполненные — с `value: ""` (в отличие от общего правила «пустые ключи не приходят»). Точечное чтение — `GET /TaskAttributes?taskID=…&attributeID=…`: `200`, плоский список `{tenantID, taskID, attributeID, attributeName, value, domain, listOfValues}`. Без `taskID` фильтр по `attributeID` тоже работает (с `Range`). Значение `MultiSelect` пришло строкой (`"33"`), значение поля-списка — ключом `listOfValues` строкой (`"2"`), не текстом (2026-10-22, тенант 192; 2026-11-10, тенанты 55 и 57).

⚠ `POST /TaskAttributes` пишет доп.поле и в **закрытую** заявку (9 405 заявок на стадии «Закрыта», отказов нет; 2026-10-28, тенант 151). Что запись того же значения, что уже стоит, сервер не перезаписывает, — со слов мейнтейнера (2026-10-26), историей правок не проверено.

⚠ `GET /Tasks/{taskID}/stages` отдаёт **массив** переходов `{taskStageFrom, taskStageTo, taskStatus, dateFrom, dateTill?, changeSet[]}`, новые первыми; у текущей записи `dateTill` нет; `dateFrom` — UTC. В swagger ответ объявлен одиночным `ListStagingHistoryResult` другой формы — не совпадает с живым (2026-10-26, тенант 151).

⚠ `GET /Tasks/{taskID}/changes` — список записей `{sortOrder, uid, occured, operation, tab, section, applicationID, user{id, name}, previousSnapshot, currentSnapshot, diff}`, по возрастанию `occured`. Ключи снимков — с заглавной (`currentSnapshot.TaskStage{ID, Name}`). Форма `diff` зависит от операции: у `UPDATE` — `{ID: [было, стало], …}`, у `INSERT` — список; надёжнее брать `currentSnapshot`. `section=Stage` — только переходы, первая запись — `INSERT` со стадией создания. `section=Results` → `204`; история чек-листов лежит в `tab=CheckLists`, `section: Main`, значение пункта-списка там — текст в кавычках JSON, а не ключ. `Range` работает (`items=7-9` → `206 items=7-8/8`, за концом — `204`); без `Range` — `200` без `Content-Range` со всей историей. Несуществующая заявка — `204`. Запись через API — `applicationID: 4`, веб-интерфейс — `3` (2026-10-06, тенант 1; 2026-10-22, тенант 192).

⚠ `GET /Tasks/{taskID}/conversations` принимает `isExternal=true|false` — в swagger параметра нет, но фильтр работает; пусто — `204`. `id` сообщения — **локальный** номер в чате заявки (1..N), не глобальный. Число сообщений без вычитки — `HEAD /Tasks/{taskID}/conversations` → `Content-Range: items=0-0/N` (2026-10-12, 2026-10-15, тенант 192).

⚠ `id` выполненной работы в `completedWorks` заявки — тоже локальный. `GET /Tasks/{taskID}/completedWorks/materials` — словарь по `completedWorkID`, `Range` игнорирует (`200` без `Content-Range`). Вложения работ — только `GET /Tasks/{taskID}/completedWorks/attachments`, в «Файлах» заявки их нет (2026-10-15, тенант 192).

⚠ `GET /Tasks/{taskID}/checkLists/{taskCheckListID}/results/v2`: у нетронутого пункта `isChecked: false`, `value: []` — `null` («не обработан» по схеме) не встретился ни разу на 842 пунктах; «не трогали» и «сняли флажок» не различить (2026-10-06, тенант 1).

⚠ `POST /TaskAssignmentHistory` массивом из N записей на одну заявку — **одна** группа из N исполнителей, а не N назначений подряд; новая группа **заменяет** прежних исполнителей (прежняя уходит в историю). Недопустимый пользователь — `201` и частичный успех: у его элемента в `assignments` поле `"error": "UserNotFound"`, остальные назначены — отказ виден только в теле (2026-11-10, тенант 1).

## Наиболее используемые

`GET /Tasks`, `POST /Tasks`, `GET /Tasks/{taskID}`, `PATCH /Tasks/{taskID}`, `POST /TaskStagingHistory`, `GET /Tasks/{taskID}/stages/next`, `POST /CompletedWorks` — расшифровка в [overview.md](../overview.md).
