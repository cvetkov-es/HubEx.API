# HubEx.API — доменный репозиторий API HubEx для ИИ-агентов

> **Статус:** спека на ревью мейнтейнера 2026-07-14. Следующий шаг — план реализации (writing-plans).
> **Область:** три новых репозитория — `HubEx.API` (контент), `HubEx.API.Pipeline` (пайплайн обновления, сабмодуль `tools/`), `HubEx.API.CLI` (живой доступ, сабмодуль `cli/`).
> **Автор решений:** Евгений Цветков (мейнтейнер).
> **Происхождение:** выделение API-домена из монорепы `HubEx.AI-2.0` по образцу `HubEx.Wiki` (спеки 2026-07-13 hubex-wiki-repo и 2026-07-14 split-pipeline-submodule). Монорепа в этом цикле **не меняется**.
> **Размещение этого файла:** `docs/superpowers/` по образцу вики живёт в пайплайн-репо; на время бутстрапа лежит здесь и переезжает в `HubEx.API.Pipeline` при его создании.

## 1. Зачем

Монорепа `HubEx.AI-2.0` собирала все источники (API, БД, продукт, вики) в один репозиторий — для шаринга это неудобно. Вики уже выделена (`HubEx.Wiki`); API — второй домен.

Главный потребитель `HubEx.API` — **клиентские ИИ-агенты, ищущие нужные ручки** HubEx API. Приоритет цикла — пайплайн, дающий из swagger **очищенные данные**: сырые выгрузки (0.1–1.2 МБ на сервис) агенту целиком нечитаемы, а рукотворные дистилляты не гарантируют полноту. Второй потребитель — внутренние агенты автоматизаций (живой доступ с кредами) — получают то же ядро плюс сабмодуль CLI.

## 2. Решения (принятые)

| Решение | Выбор | Почему |
|---|---|---|
| Состав | **три репо**: контент + пайплайн (сабмодуль `tools/`) + живой CLI (сабмодуль `cli/`) | Читателю знаний — чистый клон без кода; обновление и живой доступ — независимые инструменты с разными потребителями, каждый подключается точечным `submodule update --init <path>` |
| Живой CLI | **отдельный репо `HubEx.API.CLI`**, сабмодулем `cli/` | Решение мейнтейнера («CLI вынес бы в отдельный модуль»); креды и запись — не для клиентского клона |
| `db query` / `hubex_core/db.py` / dbconfig | **не берём** | Домен БД; остаётся в монорепе до выделения `HubEx.DB` |
| Снапшоты swagger | **в контент-репо** (`snapshots/`), канонические, сырые | Вербатим-слой домена (аналог `pages/` у вики): база диффа и точный источник схем; в сабмодуле каждое обновление данных требовало бы коммита в пайплайн + бампа пина |
| Очищенный слой | **`endpoints/<SVC>.md` — детерминированная генерация из swagger, без модели** | Гарантированная полнота для поиска ручек; модельная генерация убила бы доверие к полноте |
| Слой опыта | **`notes/<SVC>.md`** (наследник `knowledge/api/services/*.md`) | «Что узнали на практике» отдельно от «что говорит swagger»; сюда агенты пишут находки |
| Роль модели в обновлении | **точечная правка `notes/` по диффу**; полная регенерация запрещена промптом | Не затирает накопленные находки (у вики тот же принцип отложенного overview) |
| `entity-map.md` | едет в контент-репо, **строки «БД:» удаляются** | Репо — лист без ссылок наружу; факты чужого домена без db-репо тихо гниют |
| Миграция | **свежие репо, перенос копированием**; git-история остаётся в монорепе-архиве | История `tools/` перемешана между доменами, чисто не режется; история знаний API короткая |
| Монорепа | **не трогаем вообще** | Как при выделении вики; переход монорепы на сабмодули — отдельный будущий цикл |
| Хостинг | **host-agnostic**, относительные submodule-URL `../HubEx.API.Pipeline`, `../HubEx.API.CLI`; все репо у одного владельца; первый хост — GitHub | Как у вики: URL резолвится от origin суперпроекта, перенос хоста не трогает `.gitmodules` |
| Формат `endpoints/` | **утверждается пилотом** (§9) до массового засева | Требование мейнтейнера: обработать один сервис тестово, посмотреть и переделать |
| llms.txt | **генерится пайплайном**: `llms.txt` (индекс по [llmstxt.org](https://llmstxt.org)) + `llms-full.txt` (склейка `endpoints/`) в корне контент-репо | Запрошено мейнтейнером: параллельная выдача в формате llms.txt для внешнего использования |

**Явно вне среза:** домен БД (`HubEx.DB`); комбо-репозитории; правки монорепы; cron/CI и submodule-авторизация в CI; бенчмарки качества; авто-коммит; генерализация пайплайна с вики-пайплайном (у них разные источники и швы; общие модули `report`/`model_client` — осознанный форк, как решено для вики).

## 3. Конечное состояние

**HubEx.API** (контент, лист — ссылок наружу нет):

```
HubEx.API/
├── README.md · CLAUDE.md · AGENTS.md   ← роутер (образец — HubEx.Wiki)
├── overview.md          ← путеводитель по API: авторизация, кросс-тенант, пагинация,
│                          карта 22 сервисов, типовые сценарии → сервисы, топ-ручки
├── entity-map.md        ← сущность → ручки + грабли (без строк «БД:»)
├── endpoints/<SVC>.md   ← полный детерминированный справочник ручек (22 файла)
├── notes/<SVC>.md       ← курируемые заметки практики (грабли, правила, связки)
├── snapshots/<SVC>.json ← канонические swagger (вербатим; целиком не читать)
├── llms.txt             ← индекс по llmstxt.org (генерится пайплайном)
├── llms-full.txt        ← полная склейка endpoints/ одним файлом (генерится)
├── .gitignore           ← .superpowers/, __pycache__/, .pytest_cache/
├── .gitmodules          ← tools → ../HubEx.API.Pipeline · cli → ../HubEx.API.CLI
├── tools/               ← сабмодуль (пуст без init)
└── cli/                 ← сабмодуль (пуст без init)
```

**HubEx.API.Pipeline** (`tools/`): `api_cli.py` (подкоманда `update`), `update/` (manifest · fetch · diff · endpoints_gen · notes_patch · guard · model_client · report · pipeline · prompts/), `lint/check_links.py`, `tests/`, `conftest.py`, `pytest.ini` (`testpaths = tests`), `requirements.txt`, `README.md`, `.gitignore` (`update/drafts/`, `__pycache__/`, `*.pyc`, `.pytest_cache/`), `docs/superpowers/` (specs/plans, включая эту спеку).

**HubEx.API.CLI** (`cli/`): `hubex_cli.py` (команды `api get/write`, `tenants sync/list` — без `db`), `hubex_core/` (auth · api · config · safety · tenants — **без db.py**), `tenant_base_url_overrides.yaml`, `tenant_notes.yaml`, safety-правила (перенос `knowledge/rules/safety.md` в README или `SAFETY.md`), свои `tests/`, `requirements.txt`, `README.md`.

Резолюция корня в пайплайне — как у вики: `Path(__file__).resolve().parents[2]` из `tools/update/*` указывает на корень суперпроекта; граница сабмодуля для файловых путей невидима. Команды запускаются из корня `HubEx.API`: `python3 tools/api_cli.py update ...`, `python3 cli/hubex_cli.py api get ...`.

## 4. Слои данных и путь агента

| Слой | Источник | Кто пишет | Полнота |
|---|---|---|---|
| `snapshots/` | swagger как есть (canonical JSON) | пайплайн, перезапись | 100%, но большой — только точечный grep/вырезка |
| `endpoints/` | генерация из snapshots | пайплайн, **перезапись целиком, руками не правится** | 100% ручек, компактно |
| `notes/` | практика использования | агенты/человек по ходу задач; модель — точечные правки при обновлении | выборочная: только то, чего нет в swagger |
| `overview.md`, `entity-map.md` | ручная курация (перенос из монорепы) | человек/агент | навигационная |

Путь клиентского агента: `README` (роутер) → `overview.md` (какой сервис) → `endpoints/<SVC>.md` (найти ручку, параметры) → `notes/<SVC>.md` (грабли и правила) → точечно `snapshots/<SVC>.json` (точная схема, grep по имени).

Правила в роутере (README + дубль критичного в CLAUDE.md/AGENTS.md):
- `endpoints/**` и `snapshots/**` руками не правятся — их ведёт пайплайн.
- **Нашёл особенность/правило, которого нет в swagger, — запиши в `notes/<SVC>.md`** (⚠-строка в доме-стиле); кросс-сервисное — в `overview.md` или `entity-map.md`. Запрещено писать факты, противоречащие snapshots.
- Не выдумывай ручки: нет в `endpoints/` — нет в API; проверь snapshots или скажи, что не нашёл.
- Рецепт поиска: не знаешь сервис — **grep по `endpoints/`** (summary русские); `overview.md` — для выбора сервиса по сценарию.
- Снапшоты целиком не читать (0.1–1.2 МБ) — grep/точечная вырезка.
- `tools/`, `cli/` — сабмодули; клиенту не нужны, для обновления/живого доступа — `git submodule update --init <path>`.
- Живая запись в тенант — только через `cli/` с dry-run → подтверждение человека (полные правила — в `HubEx.API.CLI`).

## 5. Формат `endpoints/<SVC>.md`

Черновой формат (финализирует пилот, §9). Заголовочный блок в доме-стиле («Что здесь / Когда сюда идти / Источник / Обновлено»), `Base: {BASE_URL}/<SVC>`, далее ручки, сгруппированные по ресурсу (первый сегмент пути):

```
### CheckLists
- `GET /CheckLists` — Возвращает список активных чек-листов · права: CheckListsList · paginated
  ← query: offset, fetch, checkListQuery{...} → map<CheckListResult>
- `POST /CheckLists` — Создает чек-листы · права: CheckListAdd
  ← body: CheckListAdd[] → IdResult[]
...
## Схемы
type CheckListResult { id: uuid, name: str, isDeleted: bool,
  items: CheckListItem[] /* Элементы чек-листа */ }
```

**Входит** (смысловая потеря — ноль): `summary` целиком (русский, 100% покрытие — главный поисковый сигнал); **полномочия** и **флаг пагинации** — извлекаются структурно из шаблонного `description` операций; параметры (имя: тип, обязательность); схемы запроса/ответа по имени; схемы — компактной алиас-нотацией `type X { поле: тип }` с короткими описаниями полей как inline-комментариями (avg 36 симв.); enum-значения (+`x-enumNames`).

**Вычищается** (обвязка): HTML-теги и boilerplate описаний, `example/examples`, `xml`, `operationId`, `tags`, неймспейс-префиксы имён схем (`HubEx.Service.WORK.Api.Data....X` → `X`, коллизии — минимальным уточнением), `format`-шум (`int32`), `$ref`-обвязка.

Нешаблонный остаток `description` операции (если встретится) сохраняется как текст после summary. Ожидаемый объём: WORK ~695К JSON → ~60–80К md; остальные пропорционально.

Генерируемые файлы (`endpoints/`) — **без поля «Обновлено»** в заголовочном блоке: дату даёт git-история, а штамп шумел бы в диффах при каждом прогоне (прецедент вики — удаление `crawled_at`).

## 6. `notes/<SVC>.md`

Наследник `knowledge/api/services/*.md`, но **без справочника сигнатур** (он в `endpoints/`): остаются ⚠-грабли, правила («isDeleted всегда фильтруй явно»), типовые связки вызовов, «наиболее используемые», глоссы. Заголовочный блок в доме-стиле. Файл может быть коротким или отсутствовать — не для всех сервисов есть опыт.

Засев: модель разово (под ревью) разносит текущие дистилляты монорепы — сигнатуры выбрасывает, редакторский слой переносит в `notes/`. Первый сервис — вручную/с ревью диффа как пилот (§9). Ревизия монорепы показала: ⚠-грабель в дистиллятах почти нет (4 на 22 файла, все в WORK) — основной редакторский слой живёт в `overview.md`/`entity-map.md`; `notes/` стартуют тонкими, это норма. Дистилляты датированы 2026-07-02 и уже отстали от снапшотов 2026-07-10 — переносим только грабли/правила, не факты сигнатур.

## 7. Пайплайн (`HubEx.API.Pipeline`)

Основа — существующий `update api` монорепы (спеки 2026-07-10), изменения:

```
python3 tools/api_cli.py update [--service SVC ...] [--report-file PATH] [--recompress]

update
  → манифест doc.hubex.ru (urls[] Swagger UI) → [(service, swagger_url)]
  → per service: fetch → normalize (canonical JSON) → дифф со snapshots/<SVC>.json
       → перезаписать снапшот + ПЕРЕГЕНЕРИРОВАТЬ endpoints/<SVC>.md (детерминированно)
  → если были изменения: перегенерировать llms.txt + llms-full.txt из endpoints/
  → report: added/removed/changed по ручкам и схемам; напоминание проверить
    notes/<SVC>.md, overview.md, entity-map.md при затронутых топ-ручках
--recompress (модельный шаг):
  для changed-сервисов: промпт = дифф + затронутые фрагменты notes/<SVC>.md
    → ТОЧЕЧНАЯ правка notes (упоминания изменённых/удалённых ручек);
      полная регенерация запрещена промптом; new-ручки в notes не добавляются
  guard (детерминированный, fail-safe):
    (а) все "METHOD /path" в notes/ и endpoints/ существуют в swagger.paths;
    (б) изменённые по диффу ручки, упомянутые в notes, попали в правку
  всё unstaged — человек смотрит git diff + отчёт и коммитит
```

Отличия от монорепы: пути REPO_ROOT-относительные (`snapshots/`, `endpoints/`, `notes/` в корне суперпроекта); `api_draft.py` (скелет-черновики) замещается генератором `endpoints_gen.py` — черновики больше не нужны, их роль выполняет коммитимый слой; recompress переориентирован с полной регенерации дистиллята на точечную правку notes. Wiki- и db-код не переносится; `report.py`, `model_client.py`, `swagger_slice.py` копируются как есть. Тесты монорепы по api-модулям переносятся и дополняются тестами `endpoints_gen` (фикстуры: ручка с правами/пагинацией, схема с enum и вложенностью, коллизия коротких имён) и `notes_patch`/guard.

## 8. `HubEx.API.CLI`

Перенос из монорепы без db-части: команды `api get/write` (запись — dry-run → `--confirm`), `tenants sync/list`; `hubex_core/` (auth, api, config, safety, tenants). Safety-модель (`knowledge/rules/safety.md`) едет сюда и остаётся железным правилом README контент-репо в одну строку. Кредо-файлы/конфиги — как в монорепе (gitignored + `*.example`). Свои тесты (перенос api/auth/cli/safety/tenants-тестов).

## 9. Пилот формата (обязательный гейт перед раскаткой)

1. Реализовать `endpoints_gen`, прогнать на **SLA** (12 ручек — результат обозрим целиком) и **WORK** (стресс: 150 путей, 274 схемы, коллизии имён).
2. Мейнтейнер смотрит оба файла: полнота, читаемость, объём, что вычищено зря / что осталось лишнего. Правки формата → повторный прогон.
3. Только после одобрения — массовый засев 22 сервисов.
4. Аналогичный мини-пилот для `notes`: разнести один сервис (WORK) из монорепного дистиллята, ревью диффа, потом остальные.

## 10. Засев и миграция (порядок)

1. Каркас трёх репо: README/CLAUDE/AGENTS-роутер, `.gitignore`; создать репо у владельца (GitHub, `gh repo create`), `git submodule add` относительными URL, пины на HEAD.
2. Перенос кода в Pipeline и CLI (копированием, с правкой путей и вырезкой db/wiki-частей); тесты зелёные офлайн (`-m "not live"`).
3. Пилот §9 → утверждённый формат.
4. Засев контента: `snapshots/` + `endpoints/` первым прогоном `update`; `overview.md`, `entity-map.md` (минус БД-строки, правка ссылок), `notes/` — переносом.
5. Проверки §11; человек ревьюит и коммитит; бамп пинов сабмодулей.

## 11. Проверки / приёмка

- Голый `git clone HubEx.API` → контент на месте, `tools/`/`cli/` пусты, роутер читается, ссылок наружу нет (`check_links` чист — запускается при инициализированном `tools/`).
- `git clone --recursive` → в `tools/` и `cli/` офлайн-тесты зелёные; `python3 tools/api_cli.py update` печатает отчёт (сеть); повторный прогон сразу после засева → все unchanged, рабочее дерево чистое (идемпотентность).
- `python3 cli/hubex_cli.py api get ...` работает на тестовом тенанте; `db` -команды отсутствуют.
- Каждый `endpoints/<SVC>.md` содержит все ручки снапшота (guard/тест на полноту); объём файла в разумных пределах (< ~100К).
- `llms.txt` ссылается на все 22 файла `endpoints/`; `llms-full.txt` склеен из них же.
- `git submodule status` показывает пины обоих сабмодулей.

## 12. Риски

- **Формат endpoints не зайдёт с первого раза** → гасится пилотом §9 (итерации до раскатки).
- **Модельная правка notes затрёт находки** → точечный дифф + запрет полной регенерации промптом + guard (б) + unstaged-ревью.
- **Инверсия сабмодуля** (tools пишет в суперпроект): приемлемо, запуск локальный (прецедент вики).
- **Расхождение endpoints ↔ snapshots** (правили руками / упал прогон): оба пишутся одним прогоном атомарно по сервису; тест на полноту в приёмке.
- **Коллизии коротких имён схем** при срезе неймспейсов → детерминированное правило уточнения, тест в пилоте.
- **Забытый `submodule --init`** → команда падает понятной ошибкой; README предупреждает.
