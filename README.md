# HubEx.API — справочник API HubEx для ИИ-агентов

> **Что здесь:** автономный справочник REST API HubEx: полный каталог ручек 22 сервисов (`endpoints/`), точные схемы типов (`schemas/`), заметки практики (`notes/`) и пайплайн обновления. Отдача наружу в формате llmstxt.org — производный экспорт (см. «Обновление»), в репо не коммитится.
> **Когда сюда идти:** нужна ручка HubEx API, её параметры или правила работы с API — начни с [overview.md](overview.md).

**HubEx** — облачная мультитенантная FSM-платформа (Field Service Management) для выездного обслуживания: заявки с жизненным циклом, объекты/оборудование, исполнители, SLA, чек-листы, акты, склад, аналитика.

## Правила

- `endpoints/**`, `schemas/**`, `examples/**`, `xref.md` руками не правятся — их перезаписывает пайплайн из swagger. `endpoints/`/`schemas/` неполны по замыслу: генератор осознанно вычищает `Authorization`/`Range`/`offset`/`fetch`, коды `401`/`403`, описания параметров, `example` — их отсутствие в `endpoints/` не значит «нет в API», сверяйся со swagger/живым вызовом.
- **Нашёл особенность/правило, которого нет в swagger, — запиши в `notes/<SVC>.md`** (⚠-строка: ссылка на ручку, тире, факт). Кросс-сервисное — в `overview.md`. Запрещено записывать факты, противоречащие наблюдаемому поведению API (не `endpoints/`/`schemas/` буквально — см. выше).
- Не выдумывай ручки: нет в `endpoints/` — нет в API (это про сами ручки; про их параметры/коды/заголовки — см. пункт выше); скажи, что не нашёл.
- Рецепт поиска: не знаешь сервис — grep по `endpoints/` (summary русские); `overview.md` — выбор сервиса по сценарию; сущность/связь — маршрут `xref.md` → `endpoints/<SVC>.md` (оглавление → секция) → `schemas/<SVC>.md` → `notes/<SVC>.md`.
- Живая запись в тенант — только через `cli/` с dry-run → подтверждение человека (правила — в сабмодуле `cli/`).

## Обновление и живой доступ

`tools/` и `cli/` — git-сабмодули (репозитории `HubEx.API.Pipeline` и `HubEx.API.CLI` рядом, у того же владельца). Обычный `git clone` их не тянет — потребителю справочника они не нужны. Выкачать: `git submodule update --init tools` (или `cli`, или клон с `--recursive`).

⚠ `git submodule update --init tools` оставляет `tools/` в detached HEAD — снапшоты (`tools/snapshots/`) теперь коммитятся туда же, и коммит из detached HEAD молча теряется при следующем `submodule update`. Перед `update`/`regen`: `git -C tools checkout main`.

python3 tools/api_cli.py update [--service WORK ...] [--recompress]   # забрать swagger, обновить снапшоты пайплайна и endpoints/schemas/examples/xref.md (детали: tools/README.md)
python3 tools/api_cli.py export-llms [--out dist]                     # экспорт llms.txt/llms-full.txt + копии в dist/ (не коммитится)
python3 cli/hubex_cli.py api get --tenant N /WORK/Tasks               # живой доступ (детали: cli/README.md)

`export-llms` — операция мейнтейнера: собирает в `dist/` (в `.gitignore`) самодостаточный набор в формате [llmstxt.org](https://llmstxt.org) для отдачи по HTTP. В самом репозитории llms не хранятся — это производный артефакт, генерируется перед выкладкой.

Провенанс: пин сабмодуля `tools` — единственное, что связывает версию справочника с версией снапшотов, и держится дисциплиной коммитера. Проверка мейнтейнера, что контент воспроизводим из запиненных снапшотов: `python3 tools/api_cli.py regen && git diff --exit-code endpoints schemas examples xref.md` (пусто = контент и пин синхронны).

## Комбинирование с другими доменами

Репозиторий — лист контента: на другие домены знаний не ссылается и подключается сабмодулем в комбо-репозитории (API+вики и т.д.). Инструменты мейнтейнера (`tools/`, `cli/`) подключены сабмодулями и в обычный клон не тянутся — их каталоги остаются пустыми. Соседний домен: `HubEx.Wiki`.
